3) THE REPEATABLE PER-CLASS PATTERN  (how S7/S8/S9 were done - copy it)
--------------------------------------------------------------------------------
 For class X with specs [s0,s1,s2(,s3)], create
 modules/mod-psychobot/src/classes/<x>/ with THREE units:

 (a) <X>Triggers.{h,cpp}: only the class-specific conditions the rotation keys
     off (resource thresholds, proc auras, disease/debuff missing, execute
     window). Each trigger READS core VALUES BY NAME via the context:
        ctx->GetValue<float>("power", std::to_string(POWER_xxx))   // resource %
        ctx->GetValue<bool>("has aura", "Spell Name")              // self aura
        ctx->GetValue<bool>("target has aura", "Spell Name")       // target aura
        ctx->GetValue<bool>("spell ready", "Spell Name")           // known+offCD
        ctx->GetValue<Unit*>("current target"), ("party member to heal")
     Register them in a NamedObjectContext<Trigger> via RegisterX Triggers().

 (b) <X>Strategies.{h,cpp}: a GenericXStrategy base + one Strategy per spec +
     a GenericXNonCombatStrategy. Each spec strategy overrides:
        NextAction** GetDefaultCombatActions()  // the spell PRIORITY list
        void InitCombatTriggers(std::list<TriggerNode*>&)  // trigger->action
     Wire with:
        triggers.push_back(new TriggerNode("trigger name",
            NextAction::Array(1, new NextAction("cast melee::Spell Name", REL),
                              nullptr)));
     Relevance scale: ACTION_NORMAL=10 (see engine/AiObject.h enum). Higher wins.
     Heals use ACTION_LIGHT/MEDIUM/CRITICAL_HEAL (60/70/80); emergencies 90.
     ALL casting is done via the keystone family by NAME - there is NO per-spell
     C++. e.g. "cast::Frostbolt", "cast melee::Mortal Strike",
     "cast heal::Holy Shock", "cast self::Recklessness", "cast melee aoe::Whirlwind".
     Register in a NamedObjectContext<Strategy> via RegisterX Strategies().

 (c) <X>AiObjectContext.{h,cpp}: namespace X { RegisterContext(ctx) calls the two
     registrars; CombatStrategyForSpec(specIndex) maps 0/1/2(/3) -> strategy name }.

 (d) WIRE into ai/PsychobotAiFactory.cpp (3 spots):
        CreateContext():        case CLASS_X: X::RegisterContext(context); break;
        InitCombatEngine():     if (classId==CLASS_X){ AddStrategy("<x>");
                                  AddStrategy(X::CombatStrategyForSpec(specIndex));
                                  return; }
        InitNonCombatEngine():  else if (classId==CLASS_X) AddStrategy("<x> nc");

 NOTE: per-bot contexts are class-scoped, so duplicate strategy NAMES across
 classes are fine (e.g. "protection" exists for Warrior AND Paladin; "frost" will
 exist for DK AND Mage). Only the bot's own class context is layered on.

4) HOW THE ENGINE TICKS (so you can reason about it)
--------------------------------------------------------------------------------
 PsychobotMgr::UpdateAI -> PsychobotAI::UpdateAI (throttled ~250ms) ->
 EnsureSpecAndTalents (applies BfA spec, then rebuilds the combat engine so the
 right spec strategy is installed) -> picks current Engine by state -> Engine::
 DoNextAction():
   1. (re)collect triggers/multipliers from active strategies
   2. ProcessTriggers: active trigger pushes its NextAction[] into the Queue
   3. PushDefaultActions: each strategy's default actions into the Queue
   4. pop highest-relevance basket -> resolve ActionNode -> bind Action from the
      context -> apply multipliers -> if useful+possible run prerequisites first
      ("reach melee"/"reach spell"), else Execute; queue continuers; return.
 Spell names resolve to the id the bot knows via PsychobotAI::GetSpellIdByName
 (scans sSpellNameStore, case-insensitive). So everything is DB2-agnostic: if a
 name doesn't exist in the loaded client data, that one ability just no-ops.
