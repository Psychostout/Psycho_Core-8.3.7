0. THE DECISIVE ANSWER
--------------------------------------------------------------------------------
 The CODE is NOT "close" enough to mechanically port/reuse. The right move is:
   -> DOCUMENT mod-playerbots EXTENSIVELY (architecture + every subsystem +
      file-by-file map of what each does and which core APIs it touches), then
      REWRITE the engine cleanly against Psycho_Core 8.3 APIs.
 Reuse what is portable as IDEAS/ARCHITECTURE (the Strategy/Action/Value design),
 NOT as copy-paste source.

 WHY (the single most important finding):
   ServerFacade (the supposed "abstraction layer") is TINY (~2.4KB .cpp / 3.3KB
   .h, ~5 helper methods: distance/facing/chase-target/packet send). It does NOT
   abstract the core API. Therefore AzerothCore/WotLK calls (bot->CastSpell,
   GetGroup, talent/spec APIs, opcodes, etc.) are INLINED DIRECTLY across the
   ENTIRE codebase (hundreds of files). There is no seam to swap. A "port" =
   editing essentially every file -> at that point a clean rewrite is better.

3. THE CORE-ENGINE EDITS WE WILL NEED (Phase A "fork" work, in OUR src/)
--------------------------------------------------------------------------------
 (Confirmed needed from Step 11 + this review.)
  - Socketless/bot WorldSession: our WorldSession ctor requires a WorldSocket;
    must allow a bot session with no real socket and guard all socket sends.
  - Drive bot AI each world/map tick (Player has PlayerAI but isn't bot-driven).
  - Register bots in ObjectAccessor/Map so they're found like real players.
  - Bot login path (secure login equivalent) without a real client.
  - playerbots database + config plumbing.
 These are the highest-risk, most version-specific pieces and are exactly what
 mod-playerbots ships in its AzerothCore FORK (not in the module).


4. RECOMMENDED PORT STRATEGY (document-then-rewrite)
--------------------------------------------------------------------------------
 STEP 1 - DOCUMENT EVERYTHING (this is what "study every file" produces):
   Build a Dev/playerbots_docs/ knowledge base:
     a) ARCHITECTURE.md   - the Strategy/Action/Value/Trigger/Context engine,
        how PlayerbotAI ticks, how a master controls bots, random-bot lifecycle.
     b) FILE_MAP.md       - every file: path, purpose, key classes/functions,
        and (critical) which CORE APIs it calls -> our 8.3 equivalent.
     c) API_MAP.md        - a table: AzerothCore/WotLK API used -> Psycho_Core
        8.3 API. This becomes the rewrite cheat-sheet.
     d) CORE_EDITS.md     - the exact Phase-A engine changes (section 3) with
        where they go in our src/.
     e) DB_SCHEMA.md      - the playerbots DB tables -> our schema.

 STEP 2 - DESIGN OUR OWN ENGINE (clean-room from the docs, our APIs):
   Recreate the Strategy/Action/Value/Trigger/Context framework in a NEW module
   (modules/mod-playerbots-psycho or in-core), written against 8.3.

 STEP 3 - PHASE A core edits (bot sessions + tick drive + accessor + login).

 STEP 4 - VERTICAL SLICE FIRST: one class (e.g. Warrior), basic combat +
   follow + a couple of triggers/actions, a handful of bots. Prove the loop end
   to end before scaling.

 STEP 5 - SCALE OUT: more actions/values/strategies, more classes, random-bot
   manager, travel/quest, dungeon/raid AI, gear/talent factory.

 WHY clean-room-from-docs (not copy-paste):
   - No usable abstraction seam (section 0) -> copy-paste = edit every file anyway.
   - 8.3 APIs/spells/talents differ everywhere -> most lines change regardless.
   - A rewrite lets us match OUR module system + coding patterns + ServerFacade.
   - It also clarifies licensing (see section 5).


5. LICENSING (important)
--------------------------------------------------------------------------------
 mod-playerbots / ServerFacade headers: "Copyright (C) 2016+ AzerothCore,
 released under GNU AGPL v3". NOTE: that is AGPL v3, which is STRONGER/STICKIER
 than GPLv2 (our TrinityCore base is GPLv2).
   - COPYING their source (or close derivatives) pulls AGPLv3 obligations in.
   - A clean-room REWRITE that reimplements the *ideas/architecture* (which are
     not themselves copyrightable) in our own code avoids copying their
     expression. Document from behavior/structure; write fresh source.
   - Either way the bot code is NOT yours under LICENSE.MYCODE if it derives
     from their expression. A genuine clean-room rewrite you author can be
     LICENSE.MYCODE for the parts you write from scratch (with care re: AGPL).
   - RECOMMENDATION: treat this as clean-room (docs -> fresh code), and get
     comfortable that the safest legal stance is your own implementation, not a
     line-by-line translation. (Not legal advice.)


6. BOTTOM LINE
