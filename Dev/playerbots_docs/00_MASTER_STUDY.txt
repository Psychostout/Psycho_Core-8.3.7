2. THE AI ENGINE (ike3 Strategy/Action/Value/Trigger) - LEARN THIS
--------------------------------------------------------------------------------
 Core types (playerbot/strategy/):
   - Engine        : per-bot brain. Holds active Strategies, runs a tick:
                     evaluate Triggers -> queue Actions (ActionBasket/Queue) ->
                     execute by relevance, with Multipliers + ExecutionListeners.
   - Strategy      : a named bundle that wires Triggers->Actions (e.g. "dps",
                     "tank", "heal", "nc"(non-combat), "follow master").
   - Action        : a unit of behaviour. Key virtuals:
                       Execute(Event&), isPossible(), isUseful(),
                       getPrerequisites()/getAlternatives()/getContinuers()
                       (the P/A/C action-node chains), getRelevance(),
                       getThreatType(), Reset().
   - Value<T>      : cached "fact" the AI reads (nearest enemy, health %, has
                     aura, current target, etc.). Lazy + cached per tick.
   - Trigger       : a condition; when true it pushes its action(s) into the
                     queue with a relevance.
   - AiObjectContext: the REGISTRY. NamedObjectContext<Action/Value/Trigger/
                     Strategy> maps string names -> factory creators. This is how
                     "cast fireball" / "low health" / "enemy target" resolve.
   - Multiplier / PassiveMultiplier: scale action relevance (e.g. CC, LOS).
   - ActionNode + NextAction::array(P, A, C): each spec strategy defines an
     ActionNodeFactory mapping action name -> ActionNode with:
        P = Prerequisites (do first), A = Alternatives (if this fails),
        C = Continuers (do after). (See any class strategy, e.g. DK.)
 Per-class content lives in strategy/<class>/: a <Class>AiObjectContext that
 registers that class's actions/triggers/strategies, plus spec strategies
 (e.g. BloodDK/FrostDK/UnholyDK), <Class>Actions, <Class>Triggers, Multipliers.

 => TO RECREATE: keep this ENGINE design verbatim (it's clean & core-agnostic in
    concept). Only the LEAF actions/values/triggers touch the core API.


3. THE CORE-API SEAM: ServerFacade  (THE key to "same result on our core")
--------------------------------------------------------------------------------
 playerbot/ServerFacade.h is the abstraction over the server. It is FULL OF
 PREPROCESSOR CORE SWITCHES already:
     #ifdef MANGOS ... #endif      #ifdef CMANGOS ... #endif
     #ifndef MANGOSBOT_TWO / ZERO  (expansion variants)
 Example:
     DeathState GetDeathState(Unit* u){ #ifdef MANGOS u->GetDeathState();
         #else (TWO) u->getDeathState(); #endif  #ifdef CMANGOS u->GetDeathState(); }
 It wraps: IsAlive/IsDead/DeathState, IsInCombat/IsFrozen/IsInRoots/IsCharmed/
   IsFeared, IsInFront, distance helpers, SendPacket/SendMessageToSet,
   LookupSpellInfo/LookupSpellRangeEntry/GetSpellInfoRows, LOS, IsFriendly/
   IsHostile, IsSpellReady, faction, chase target/angle/offset, BG template/
   arena type, GetAreaId, SetFacingTo.

 *** THIS IS OUR PORT STRATEGY ***
 The codebase is DESIGNED to add a new core via #ifdef. To get the SAME RESULT
 on Psycho_Core we ADD a `#ifdef TRINITY` (BfA 8.3) branch to ServerFacade and
 every other #ifdef MANGOS/CMANGOS site. ServerFacade is the FIRST and most
 important file to port - it is the contract of "what the bot needs from the
 core". Most behaviour code calls sServerFacade.* and stays UNCHANGED.

 CAVEAT: ServerFacade does NOT cover everything; many files still call core APIs
 directly (bot->CastSpell, GetMotionMaster, sSpellMgr, talent stores). Those are
 the additional port sites (sections 5-8).

5. SPELLS + SPELL RANKS  (BIGGEST EXPANSION DIFFERENCE)
--------------------------------------------------------------------------------
 HOW IT WORKS NOW (WotLK-era):
   - ChatHelper builds spellIds: map<lowerName, vector<spellId>> by scanning the
     whole SpellStore (SpellEntry.SpellName[0]). parseSpell(name) -> ids.
   - PlayerbotAI::CastSpell(name,...) resolves a name to the spell the bot KNOWS,
     picking the appropriate RANK (the bot learns ranked spells; the AI asks for
     "fireball" and the core/known-spell logic uses the highest known rank).
   - Spell ranks exist: GetFirstSpellInChain/GetPrevSpellInChain chain logic +
     sSpellMgr rank handling underpin "cast the best rank I know".
   - Class strategies reference spells BY NAME ("fireball","frostbolt",...), so
     the leaf actions are name-driven (good - names are stable-ish), but the
     RANK + KNOWN-SPELL plumbing is WotLK.

 ON BfA 8.3 (Psycho_Core) - WHAT CHANGES:
   - SPELL RANKS WERE REMOVED (since Cata/MoP). There is ONE spell per ability;
     no rank chains. -> All "highest known rank" logic must be SIMPLIFIED to a
     direct known-spell check. GetFirstSpellInChain/rank APIs differ or are gone.
   - SpellEntry/sSpellStore (DBC) -> TrinityCore uses SpellInfo via
     sSpellMgr->GetSpellInfo(id, Difficulty) (DB2/hotfix). 8.3 spells are keyed
     by (id, DIFFICULTY). The ChatHelper name->id scan must use our DB2 stores.
   - Many WotLK spell IDs differ on 8.3; class rotations reference different
     spells. (User: writing new content is fine -> we re-author class rotations.)
   - SpellName is localized differently in DB2.
   PORT TASKS:
     [ ] Rebuild ChatHelper spell-name map on our DB2 SpellName store.
     [ ] Replace rank-chain/highest-rank logic with single-spell known checks.
     [ ] Route LookupSpellInfo -> sSpellMgr->GetSpellInfo(id, DIFFICULTY_NONE).
     [ ] Re-author per-class spell name lists for 8.3 (your DK = template).

7. PATHING / MOVEMENT
--------------------------------------------------------------------------------
 HOW IT WORKS NOW:
   - MovementActions.cpp uses bot->GetMotionMaster():
       mm.MovePoint(mapId, Position(x,y,z,0), FORCED_MOVEMENT_RUN/FLIGHT, speed, fly)
       mm.MovePath(pointPath, FORCED_MOVEMENT_RUN, ...)
       mm.Clear(); top()/empty() inspection.
   - CMaNGOS MotionMaster API (MovePoint signature w/ ForcedMovement flag +
     speed + fly bool) differs from TrinityCore's.
   - TravelMgr/TravelNode (3.8k+2.8k LOC): a NAVIGATION GRAPH of travel nodes
     across the world (quest hubs, flight, transports) so bots path long distance.
   - Uses mmaps (navmesh) under the hood via the core's PathFinder.

 ON BfA 8.3 (TrinityCore) - WHAT CHANGES:
   - TrinityCore MotionMaster signatures differ:
       MovePoint(id, x,y,z, generatePath), MovePath(...), MoveSplineInit,
       MoveCharge/MoveJump etc. (see our Dev/ModuleAPI_Reference.txt section 6).
   - FORCED_MOVEMENT_* flags are a CMaNGOS concept -> map to TC equivalents.
   - PathGenerator (TC) replaces CMaNGOS PathFinder. mmaps must be extracted for
     8.3 maps (our tools: mmaps_generator).
   - TravelMgr node DB + map IDs are WotLK; many maps/coords differ on 8.3.
   PORT TASKS:
     [ ] Rewrite MovementActions move calls on TC MotionMaster/PathGenerator.
     [ ] Map FORCED_MOVEMENT_* -> TC movement flags/speeds.
     [ ] Rebuild/curate TravelMgr nodes for 8.3 maps (big data task; can start
         minimal: follow-master + local nav, expand later).

   [ ] Bot login path (PlayerbotLoginMgr equivalent) w/o a client.

10. CODE STYLE (so a rewrite matches "same result")
--------------------------------------------------------------------------------
 - C++ in `namespace ai`. Classes per file, <Name>.cpp/.h pairs.
 - Heavy use of NamedObjectFactory<T> + Context registries (string-keyed).
 - Actions/Values/Triggers are tiny single-purpose classes registered by name.
 - Core differences isolated by #ifdef MANGOS/CMANGOS/MANGOSBOT_* (we add TRINITY).
 - sServerFacade.* for wrapped calls; direct core calls elsewhere.
 - Config via sPlayerbotAIConfig (its own conf file, many keys).
 - Logging via core log macros; PerformanceMonitor/MemoryMonitor for scaling.
