1. BfA 8.3 TALENT MODEL (researched + verified vs our core)
--------------------------------------------------------------------------------
 - Talents = 7 rows (TierID 0-6) x 3 choices (ColumnIndex 0-2); rows unlock at
   levels 15/30/45/60/75/90/100. Changed only in rested areas. (wowpedia/icy-veins)
 - PvP talents = separate pool (3 chosen + 1 CC-breaker). Defer to a later stage.
 - OUR CORE (verified):
     TalentEntry { ID, TierID, ColumnIndex, ClassID, SpecID, SpellID, ... }
     sTalentStore (DB2)  +  GetTalentsByPosition(class, tier, column).
     ChrSpecializationEntry { ID, ClassID, OrderIndex, Role, ... }
     sChrSpecializationStore + GetChrSpecializationByIndex(class,index) +
       GetDefaultChrSpecializationForClass(class).
     Player: SetPrimarySpecialization(specId), ActivateTalentGroup(spec),
       LearnTalent(talentId,&onCd), GetPrimarySpecialization(),
       LearnPvpTalent(...), ResetTalents().
 => TALENT REWRITE = replace WotLK points/tabs with: pick spec -> activate spec
    -> for tier 0..6 pick a column -> LearnTalent the talent at that position.

3. ARCHITECTURE DECISION (verifiable now, fills out as data arrives)
--------------------------------------------------------------------------------
 PROBLEM: 36 hand-written rotations with exact 8.3 spell-name lists is huge AND
 cannot be validated without the 8.3.7 client DB2 (spell IDs/names) which the
 user doesn't have on this machine yet.
 SOLUTION: a DATA-DRIVEN class-AI framework:
   - PsychobotTalentMgr: BfA talent rewrite (spec + LearnTalent loop). Generic,
     works for ALL classes/specs purely from DB2 (no per-class code).
   - ClassAI (base) + a SPELL-PRIORITY rotation: each spec provides an ordered
     list of spell NAMES (builders/spenders/cooldowns) + simple conditions
     (target in melee/range, resource >= X, aura missing). The engine resolves
     names -> known spell IDs at runtime via the ServerFacade (so it self-adapts
     to whatever the client DB2 actually has; no hardcoded WotLK IDs).
   - Per class: a ClassSpec table (specId/role/rotation names). DK = FULLY
     populated vertical slice; other classes = spec rows registered + rotation
     tables stubbed with their known signature spells (ready to refine once the
     client DB2 is loaded and we can confirm names).
 BENEFIT: compiles + runs now; class content = filling string tables, not new
   C++ per spell; matches your "copy a class, edit names" workflow but data-driven.
